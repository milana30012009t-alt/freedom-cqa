# Сдача результатов: Results JSON 1.0

Два файла в репозитории команды:

| Файл | Что внутри | Когда появляется |
|---|---|---|
| `results/dev/results.json` | все 65 диалогов DEV (60 чатов + 5 звонков) | заранее, после подключения модели |
| `results/prod/results.json` | ровно 10 контрольных чатов | в последний час, после получения `group_id` |

Искусственные диалоги в эти файлы не попадают: экспорт берёт только записи из набора организаторов
(API по `group_id` или сохранённый ответ этого API). Предварительный прогон без модели пишется отдельно
в `results/preview/` (папка в `.gitignore`) и сдаваться не может.

## Формат

```json
{
  "schema_version": "1.0",
  "team_name": "…настоящее название команды…",
  "model": { "mode": "local | external_api | hybrid", "name": "…фактическая модель…" },
  "results": [
    {
      "conversation_id": "p1-ru-001",
      "status": "ok",
      "criteria": [
        { "criterion_id": "contact", "value": true, "rationale": "…", "evidence_turns": [5] }
      ],
      "score": { "final_score": 90.5, "critical_flag": false },
      "error": null
    },
    { "conversation_id": "p1-ru-002", "status": "error", "criteria": [], "score": null, "error": "причина" }
  ]
}
```

Других полей нет ни на одном уровне.

| criterion_id | Код PDF | Значение | Вес |
|---|---|---|---|
| `contact` | 01 | `true` / `false` | 10 |
| `discovery` | 02 | `true` / `false` / `null` | 15 |
| `identification` | 03 | `true` / `false` / `null` | 20 |
| `consultation` | 04 | `0` / `5` / `10` / `15` / `20` / `null` | 20 |
| `empathy` | 05 | `true` / `false` | 15 |
| `dialogue` | 06 | `0` / `4` / `7` / `10` | 15 |
| `closure` | 07 | `true` / `false` / `null` | 5 |
| `critical` | 08 | `true` / `false` | без веса, в балл не входит |

- В записи `ok` ровно 8 критериев, каждый по одному разу. `null` пишется только для N/A там, где он разрешён;
  обоснование начинается с `N/A: <какое условие выполнено>`.
- **Ошибка обработки никогда не превращается в 0 или N/A.** Если модель не ответила, ответила не по схеме
  или хотя бы один критерий не удалось оценить, запись получает `status: "error"`, `criteria: []`, `score: null`
  и причину в `error`.
- `evidence_turns` — номера сообщений с единицы по **всему** массиву `transcript` организаторов:
  клиент, бот, система, оператор. Сообщение `m<i>` в интерфейсе — это `transcript[i]`, то есть номер `i + 1`.
- Цитаты в `rationale` пишутся в «ёлочках» со временем реплики: «Меня зовут Алина» (01:10). Каждую цитату
  программа ищет в транскрипте. Если модель привела фрагмент, которого в транскрипте нет, он не выдаётся за
  цитату: в тексте стоит `[пересказ модели, дословно в транскрипте нет: …]`, а оценка помечается для проверки.
  Если процитированной реплики нет в доказательствах модели, она добавляется в `evidence_turns`.

### Как считается `final_score`

Считает программа, модель баллы не считает.

```
final_score = 100 × Σ(вес × доля) / Σ(вес)    по критериям с весом и значением ≠ null
доля: true = 1, false = 0, consultation = value / 20, dialogue = value / 10
```

N/A (`null`) исключается, и его вес пропорционально распределяется между остальными критериями. Итог округляется
до двух знаков (половина вверх). `critical` в балл не входит и его не обнуляет; `score.critical_flag` всегда равен
`critical.value`.

Пример: всё выполнено, `consultation = 15`, `dialogue = 7` → (10 + 15 + 20 + 15 + 15 + 10,5 + 5) / 100 → **90.5**.
Тот же диалог с `discovery = null` → 75,5 / 85 → **88.82**.

Валидатор пересчитывает балл независимо, в целых числах без плавающей точки. Тест сверяет этот пересчёт с основным
движком на 5000 случайных комбинациях.

## Поле `model`: только то, что реально оценивало

- Файлы `results/dev` и `results/prod` формируются **только при подключённой модели**. Без модели
  `npm run export:dev` останавливается с кодом 2 и ничего не записывает.
- `name` берётся из ответа API модели (поле `model`, которое возвращает сервер); если сервер его не прислал, берётся
  настроенное имя модели. `mode` определяется по адресу, на который реально уходили запросы:
  `localhost`, `127.0.0.1`, `*.local` и частная сеть дают `local`, любой другой адрес — `external_api`. Если записи
  оценены моделями из обеих групп — `hybrid`. Для подписки Claude через Claude Code (`AI_PROVIDER=claude-code-cli`)
  `mode` = `external_api` (модель работает на серверах Anthropic), `name` — модель, которую Claude Code указал в своём
  ответе (`modelUsage`), например `claude-sonnet-5-5`.
- Офлайн-правила моделью не считаются. Их прогон (`--engine rules`) пишется в `results/preview/` с именем
  `NO-LLM offline rules … — preview, not for submission`, а валидатор в режиме сдачи такой файл отклоняет.
- Если во время экспорта модель упала на части диалогов, эти записи получают `status: "error"`.
  В правила они не подменяются. Если модель не оценила ни одного диалога (неверный ключ, нет сети, модель не запущена),
  экспорт завершается с кодом 5 и файл не записывает: прежний файл остаётся без изменений.

### Подключение модели (в `.env`, ключи не выводятся и не попадают в Git)

**Подписка Claude Pro/Max через Claude Code (external_api, без оплаты API):**
```
AI_PROVIDER=claude-code-cli
CLAUDE_CODE_MODEL=sonnet
AI_CONCURRENCY=1
AI_TIMEOUT_MS=600000
```
Нужен установленный Claude Code с входом через подписку (`claude auth login --claudeai`). Ключ API не нужен: проект
убирает `ANTHROPIC_API_KEY` и другие учётные данные API из окружения Claude Code, запускает его из пустой папки,
без инструментов (`--tools ""`), без пользовательских настроек (`--setting-sources ""`) и без сохранения сессий,
перед первым вызовом проверяет `claude auth status` (`authMethod = claude.ai`), а в каждом вызове — что Claude Code
сам сообщает `apiKeySource: none`. Расход идёт из лимитов подписки. Порядок для подписки:
`npm run check:model` (1 диалог) → `npm run check:model -- --sample` (RU, KZ, EN) → `npm run export:dev`.
Без успешного пробного прогона полный экспорт не запускается (код 7). При достижении лимита экспорт останавливается
(код 6), ничего не записывает и при повторном запуске продолжает с места остановки: диалоги, уже успешно оценённые той
же моделью с тем же промптом, чек-листом и транскриптом, повторно не отправляются (`--fresh` — отправить заново).
Пошагово — [MACBOOK.md](MACBOOK.md).

**Claude API (external_api, платно):**
```
ANTHROPIC_API_KEY=…
ANTHROPIC_MODEL=claude-sonnet-5-5
```

**Локальная модель через Ollama (local), на MacBook:**
```zsh
brew install ollama && ollama serve &          # или приложение Ollama
ollama pull qwen2.5:14b                        # или другая модель, которая влезает в память
```
```
AI_PROVIDER=openai
OPENAI_BASE_URL=http://localhost:11434/v1
OPENAI_MODEL=qwen2.5:14b
OPENAI_RESPONSE_FORMAT=json_object
```

Проверка без вывода ключа: `npm run preflight`.

Качество и скорость локальной модели здесь не измерялись. Прогоните DEV заранее, засеките время и посмотрите,
сколько записей получили `error`.

## Команды

| Команда | Что делает | Код выхода |
|---|---|---|
| `npm run preflight` | TEAM_NAME, модель, адрес API (только хост), файлы, Git: ветка, remote, `ls-remote`, что результаты не в `.gitignore`, а `.env` и данные не в репозитории | 0 / 1 |
| `npm run check:model` | пробный прогон: 1 диалог (`-- --sample`: RU, KZ, EN) с проверкой по формату 1.0; файлы сдачи не меняются | 0 · 1 не пройден · 2 нет модели · 6 лимит / вход |
| `npm run export:dev` | 65 диалогов DEV → оценка моделью → `results/dev/results.json` → проверка | 0 · 1 нет названия команды / данных · 2 нет модели · 3 не 65 · 4 не прошла проверку · 5 модель не оценила ни одного диалога · 6 прогон остановлен (лимит подписки, вход) · 7 нет пробного прогона (подписка); при 5–7 файл не записан |
| `npm run export:prod -- --group <ID>` | свежая загрузка `<ID>` из API → ровно 10 → оценка → `results/prod/results.json` → проверка | то же, 3 = не 10 |
| `npm run validate:results` | строгая проверка обоих файлов по данным организаторов | 0 / 1 |
| `npm run export:dev -- --engine rules` | предварительный прогон без модели → `results/preview/dev.rules-preview.json` | — |

Дополнительные ключи: `--file <сохранённый ответ API>` (если API недоступен), `--team "…"` (вместо TEAM_NAME),
`--fetch` (для DEV: скачать набор заново), `--allow-count` (только если организаторы официально изменили число
диалогов).

Экспорт пишет файл атомарно: сначала во временный файл, затем переименование, так что оборванный запуск не оставит
половину JSON. Записанные байты сразу проверяются валидатором. В `data/results-manifest.json` сохраняются
`group_id`, sha256, модель, число ok/error и результат проверки.

## Что проверяет валидатор

`server/results/validator.js` написан отдельно от экспорта. У него своя таблица критериев и свой пересчёт балла.
Он проверяет:

- UTF-8 без BOM, корректный JSON, ровно 4 поля верхнего уровня, `schema_version = "1.0"`;
- `team_name` заполнен и не заглушка («Название команды», TODO, …);
- `model.mode` из списка; `model.name` — не заглушка и не офлайн-правила;
- число записей: 65 или 10, без повторов `conversation_id`, каждый ID есть в наборе организаторов,
  и для каждого диалога набора есть запись;
- запись `error` строго в виде `{id, "error", [], null, причина}`; у записи `ok` поле `error = null`;
- 8 критериев без повторов и лишних, допустимые значения и типы (`"true"` строкой отклоняется), непустое
  обоснование;
- `evidence_turns`: целые числа ≥ 1, не больше длины транскрипта, без повторов, не пустые при оценке;
- каждая цитата из обоснования найдена в транскрипте (с учётом восстановления кодировки);
- `final_score` — число 0–100, не больше двух знаков, совпадает с независимым пересчётом; `critical_flag = critical.value`.

Структурная JSON Schema: `schemas/results-1.0.schema.json` (draft 2020-12). Сторонняя перекрёстная проверка:
`python3 scripts/check-schema.py results/dev/results.json results/prod/results.json`, нужен `pip3 install jsonschema`.
В схеме нет `multipleOf: 0.01`: из-за двоичной арифметики он ложно отклоняет 1363 из 10001 корректных значений
(например, 0.07). Два знака проверяет валидатор.

Тесты (`tests/unit/results-json.test.js`) прогоняют 47 намеренно испорченных вариантов файла, а также BOM,
битый UTF-8 и обрезанный JSON. Каждый вариант должен быть отклонён с конкретным сообщением.

## Подготовка до последнего часа

1. `cp .env.example .env`, заполнить `TEAM_NAME`, ключ или адрес модели, `DATASET_API_URL`.
2. `npm run preflight` — все пункты зелёные, кроме «results/prod ещё нет».
3. `npm run export:dev` → код 0. Посмотреть число `error`; при необходимости повторить.
4. `npm run validate:results` → DEV пройдена.
5. `git add results/dev/results.json && git commit -m "DEV results" && git push` — проверить, что push проходит.
6. Засечь, сколько занял DEV (65 диалогов): 10 диалогов займут примерно 1/6 этого времени.

После получения контрольных диалогов программа не меняется. Меняется только `group_id` в команде.

## PROD за один час

| Время | Шаг |
|---|---|
| 0:00 | Получить `group_id` контрольного набора. Если для него дан другой адрес API, заменить `DATASET_API_URL` в `.env` |
| 0:02 | `npm run export:prod -- --group <ID>` — загрузка из API, проверка «ровно 10», оценка, запись, валидация |
| ~0:15 | Код 0 → дальше. Код 3 → неверный `group_id` или неполный ответ API; код 2 → модель не подключена; код 4 → прочитать ошибки |
| | Если среди 10 есть `error` (сбой модели), повторить ту же команду: файл перезапишется целиком |
| 0:20 | `npm run validate:results` — DEV и PROD пройдены |
| 0:22 | `git add results/dev/results.json results/prod/results.json` |
| 0:23 | `git commit -m "PROD results: <ID>"` и `git push` |
| 0:25 | Открыть репозиторий на GitHub и убедиться, что оба файла на месте |

Запасной вариант, если API недоступен: сохранить ответ GET в файл (вне репозитория) и запустить
`npm run export:prod -- --group <ID> --file ~/Downloads/control.json`.

Файлы руками не править: любая правка ломает пересчёт и проверку. Если что-то не так, перезапустите экспорт.

## Допущения, которые нужно сверить с приложением организаторов

Сделано по тексту задания этапа. Если в приложении к заданию описано иначе, поменять нужно только
`server/results/official-format.js` и валидатор:

- в записи `ok` есть поле `"error": null`, в записи `error` — `"score": null`;
- `score` содержит только `final_score` и `critical_flag`;
- критерии идут в порядке 01–08 (порядок не проверяется, проверяется состав).
